# Base-plate material picker — design

Status: approved by user 2026-08-26, ready for implementation planning.

## 1. What this is

Add a picker to the start screen that lets the player choose the visual
material of the game board's base plate (井体底座), among 5 options:

- **玻璃** (glass) — the existing look, unchanged: `UnlitMaterial`,
  `BlendingMode.TRANSPARENT`, warm-neutral base color at
  `GROUND_OPACITY = 0.80f` (see `BoardCubeRenderer.attachGround`).
- **Wood_02**, **Tiles_04**, **Wood_12**, **Travertine_09** — four new PBR
  materials supplied by the user as `/Users/zohar/Downloads/Base.usdz`.

Purely visual. Does not touch game logic, board geometry, or the falling-piece
material (candy colors stay as they are).

## 2. Background: what `Base.usdz` actually contains

The user's original description ("一个模型带 4 种材质") does not match the file.
Unpacked with `unzip` + `usdcat` (the project's usual last-resort verification
step for `.usdz`, per `usd-python-binding-is-x86-use-usdcat` — the `pxr` Python
binding on this machine is x86 and crashes, so inspection goes through the
system `usdcat` + manual unzip instead):

- `Base.usdz`'s `Root` has 4 child prims, each a `prepend references` to a
  **separate, independent** nested `.usdz`: `Wood_02.usdz` (9.2M),
  `Tiles_04.usdz` (13M), `Wood_12.usdz` (17M), `Travertine_09.usdz` (9.4M).
- Each nested `.usdz` contains **only a `Material` scope — no mesh/geometry at
  all**. `customLayerData` shows `Version = "Spatial Editor V6.0.1"` /
  `"V0.10.0"` — these are material-library exports from PICO Spatial Editor,
  not models.
- Each material is a **Shader Graph** (`materialType = "SHADER_GRAPH"`,
  `shaderGraphGuid`), built on `ND_UsdPreviewSurface_surfaceshader` (standard
  metallic/roughness PBR) with a small MaterialX node graph (texture-coordinate
  tiling, a color-tint multiply, swizzles) feeding `diffuseColor` / `metallic`
  / `roughness` / `normal`.
- Each material ships 3 textures at **2048×2048**: `*_Color.png`,
  `*_Normal.png`, `*_Roughness.png` (~9.5MB per material). `metal_texture`
  points at a constant black JPEG, i.e. these are non-metallic (dielectric)
  surfaces.
- Each nested `.usdz` also carries a 256×256 `thumbnail/thumbnail.usdz.png` —
  reused for the picker's swatch images (see §5).

### Why this rules out a pure-code approach

`PhysicallyBasedMaterial` (plain code, no Editor) could reproduce this
reasonably closely using the 3 raw textures directly. That was the initial
recommendation. **The user explicitly chose the higher-fidelity path instead**:
per `pico-dev-knowledge` (`spatial-sdk_rendering_shadergraphmaterial.md`),
`ShaderGraphMaterial` "can only exist in the AssetBundle generated by the
Spatial Editor" — there is no runtime API to load a Shader Graph material
directly from a raw `.usdz`. Reproducing the *exact* material (including the
color-tint mix node) requires importing it into a Spatial Editor project and
exporting an AssetBundle. This is SpaceCube's first use of Spatial Editor —
the project has been pure-code ECS until now (see project `AGENTS.md`).

### Lighting risk — lower than previously documented, still unverified

SpaceCube's `AGENTS.md` ("Material / glass look") previously warned that PBR
materials would likely render dark, because the project has no IBL/lighting
setup. That finding predates this feature and doesn't account for one thing:
SpaceCube's Stage uses `StageStyle.Mixed`. Per `pico-dev-knowledge`
(`spatial-sdk_rendering_image-based-lighting.md`): *"In `StageStyle.MIXED`
mode, the stage environment lighting is inactive. To ensure visual
consistency, the system prioritizes IBL derived from the real-world
environment."* So a custom HDR cubemap is not required — the system should
supply some automatic environment lighting regardless. This is a documentation
finding, not an on-device confirmation; actual appearance must be verified on
a real headset (see §8).

## 3. UX

- New swatch row directly below the existing 慢/中/快 difficulty row on the
  `start_screen` `AttachmentPanel`, inside the same `CandyCard`.
- 5 small rounded thumbnails in a horizontal row, each with a short label
  underneath. Glass renders as a CSS-equivalent translucent gradient swatch
  (no real image); the other 4 use their extracted 256×256 thumbnails.
  Selected swatch gets a highlighted ring (same accent used for the selected
  difficulty pill).
- Labels use the raw asset identifiers as-is — "玻璃", "Wood_02", "Tiles_04",
  "Wood_12", "Travertine_09" — rather than invented Chinese names (e.g.
  "橡木"), since we have no confirmation those names actually describe each
  material's real appearance.
- Selection changes **only** from the start screen — no picker during
  play/pause/game-over. Tapping a swatch just updates the selection; it does
  not start the game.
- Default (first launch / no saved preference): **glass**.
- Purely visual — swapping materials mid-selection has no effect on
  difficulty, score, or any gameplay state.

## 4. Data model & persistence

New enum, styled like `Difficulty`:

```kotlin
enum class BasePlateMaterial { GLASS, WOOD_02, TILES_04, WOOD_12, TRAVERTINE_09 }
```

**Not** added to `GameSettings` — `GameSettings.difficulty` is deliberately
in-memory-only (resets on process restart) and reusing that pattern here would
misrepresent the requirement. This needs **true cross-restart persistence**
(confirmed with the user after they initially assumed `difficulty` already
persisted, which it doesn't).

Mirrors `HighScoreStore` / `SharedPreferencesHighScoreStore` exactly:

```kotlin
interface BasePlateMaterialStore {
    fun get(): BasePlateMaterial
    fun set(material: BasePlateMaterial)
}

class SharedPreferencesBasePlateMaterialStore(context: Context) : BasePlateMaterialStore {
    // own SharedPreferences file, e.g. "spacecube_base_plate_material"
}
```

An `InMemoryBasePlateMaterialStore` counterpart for unit tests, matching
`InMemoryHighScoreStore`.

## 5. Asset pipeline (Spatial Editor)

1. Import the 4 material `.usdz` files into a new Spatial Editor project for
   SpaceCube (first-time Editor use for this project — driven through the
   `spatial-editor` skill / `pico-spatial-editor` MCP, not by hand-authoring
   `.usd`/`.usda` files directly, per the plugin's hard rule).
2. Organize the 4 materials in one scene (e.g. under a `MyMaterials` group),
   export as a single AssetBundle (e.g. `base_materials.bundle`) into
   `app/src/main/assets/`.
3. **Open item, confirm during implementation**: whether Spatial Editor's
   import settings can downscale the 2048×2048 textures (the user asked for a
   smaller footprint / faster load when a pure-code path was still on the
   table — worth honoring here too if the Editor exposes that control, but
   this spec does not promise a specific resolution).
4. Extract each material's 256×256 `thumbnail.usdz.png` and add as plain 2D
   drawables/assets for the picker's swatch images — **separate from** the
   AssetBundle; these are only ever used by the 2D list, never loaded as
   textures on the 3D material.

## 6. Runtime integration

- The base plate's mesh (`MeshResource.createBox` in
  `BoardCubeRenderer.attachGround`) is unchanged — only its material is
  swappable.
- Glass keeps its exact current code path untouched
  (`UnlitMaterial.create(BlendingMode.TRANSPARENT)` + existing color/opacity).
- The 4 new materials load via:
  ```kotlin
  val bundle = AssetBundle.load("asset://base_materials.bundle")
  val material = ShaderGraphMaterial.loadFromAssetBundle(bundle, "<scene>/Root/MyMaterials/<name>")
  ```
  `BlendingMode.OPAQUE` (these are solid surfaces, not translucent, unlike
  glass).
- **Lazy load**: no AssetBundle load happens for the default glass path. The
  bundle (and then the specific material) is loaded on first selection of a
  non-glass swatch, and the resulting `ShaderGraphMaterial` instance is
  cached for subsequent switches back to it. Exact loading granularity
  (whether `AssetBundle.load` itself is cheap/lazy internally, or whether it
  eagerly pulls in all packaged textures) needs confirming once the bundle
  exists — see §8.
- `ShaderGraphMaterial` does not support deep copy (per SDK docs) — since only
  one base-plate entity ever exists, this is a non-issue here.

## 7. UI implementation

- New Composable (e.g. `BasePlateMaterialPicker`) added to the `start_screen`
  panel's content, below the existing difficulty `Row`.
- SpatialUI only, wrapped in `PicoTheme`, per the project's mandatory rule —
  run the `spatial-ui-design-style` verifier before considering this done.
- Tapping a swatch: updates local UI state, persists via
  `BasePlateMaterialStore.set(...)`, and (if the game/scene is already built)
  triggers the material swap on the live base-plate entity.

## 8. Testing & verification

- Unit tests for `SharedPreferencesBasePlateMaterialStore` /
  `InMemoryBasePlateMaterialStore`, mirroring the existing
  `HighScoreStore` test pattern (host-side, no device).
- Build/install/launch on the shared emulator (device-lock protocol per this
  workspace's convention), screenshot each of the 5 selections.
- **Explicitly flagged as unverifiable except on a real headset**: how the PBR
  materials actually look under `StageStyle.Mixed`'s automatic system IBL
  (§2). Record this in `AGENTS.md`'s "Still unverified" list rather than
  claiming it from an emulator screenshot, matching this project's existing
  verification discipline (`verification-before-completion`,
  `emulator-plane-rotation-is-fake` — the emulator has known-fake behavior in
  other lighting/pose-dependent areas, so a "looks fine in the emulator"
  screenshot is not sufficient evidence here either).

## 9. Non-goals

- No mid-game or pause-menu material switching.
- No change to the falling-piece candy-color material system.
- No attempt to reproduce the exact Shader Graph node graph outside of what
  the Spatial Editor export produces — we consume the AssetBundle's output
  as-is, no hand-tuning of the graph.
- No lighting/IBL rig added by this feature — relying entirely on
  `StageStyle.Mixed`'s automatic system IBL (§2). If real-device testing shows
  the new materials look wrong, that is a follow-up, not something this spec
  solves up front.
